# iOS 方案：谷歌拼音式按键手感与按落点纠错

更新日期：2026-11-08。对应安卓 `mod` 分支提交 `ee11e5fd`。

安卓这次把谷歌拼音的触摸手感和「智能纠错」搬了过来。纠错和学习两部分放在 libime 与拼音插件里，iOS 可以直接复用；触摸部分需要在 iOS 的键盘界面里各自实现。

## 1. 直接复用的部分

| 文件 | 作用 |
| --- | --- |
| `patches/libime/0001-google-pinyin-touch-correction-and-undo-learn.patch` | 按落点给纠错定价（和谷歌一样不设代价上限，只考虑落点模型给出的邻键），纠错表加上下行邻键，撤销学习接口 |
| `patches/fcitx5-chinese-addons/0001-google-pinyin-learning.patch` | 上屏后紧接着退格撤销这次学习；回车上屏的英文加入自学习词库 |

两个补丁基于安卓仓库当前固定的子模块版本：libime `ecd23795`，fcitx5-chinese-addons `19f06898`。fcitx5-ios 已经有 `patches/libime.patch`，需要把新补丁合进去，冲突时以功能为准手工调整。

打上补丁后，iOS 无需改动即可得到：

- **撤销学习。** 上屏后下一个键是退格，就撤销这次上屏学到的词和历史。这与谷歌拼音「上屏后马上删除会降低该词词频」一致。
- **纠错表变化。** 纠错表多了上下行邻键，但没有落点数据时，上下行邻键不会被采用，行为与原来相同。

## 2. iOS 需要接入的部分：按落点纠错

### 2.1 计算落点概率

每次点按字母键，计算被按到的键和周围邻键的概率。算法与安卓 `app/src/main/java/.../input/keyboard/SpatialModel.kt` 相同，单元测试在 `SpatialModelTest.kt`，请一并移植。

- **单位换算。** 坐标换算成毫米。iOS 上用 point 乘以每毫米的 point 数，iPhone 的 UIKit 坐标约为每英寸 163pt，即每毫米约 6.4pt。
- **概率分布。** 每个键是以键中心为均值的二维高斯分布。键宽 W、键高 H 的单位是毫米，按键的整个格子都算，不只是可见的键面：
  - `varX = 0.0075 × (1.5W)² + 1.68`
  - `varY = max(0.0108 × (1.5H)² + 1.33, varX × (H/W)²)`。后一项是对谷歌的修正：谷歌的公式适合接近方形的键，我们的键约高 1.4 倍，按原公式手指偏进上下行同样比例时代价比左右邻键高得多，上下行的误触几乎纠不回来。
  - `score = ln(1 / (2π√(varX·varY))) − 0.5·(dx²/varX + dy²/varY)`
- **邻键范围。** 设 m 为最常见键宽与最常见键高中较小的一个。邻键需同时满足两个条件：键中心到被按键矩形的距离不超过 1.2m，触点到邻键矩形的距离不超过 m。
- **输出顺序。** 先放被按的键和它的分数，再按分数从高到低放邻键。

### 2.2 传给引擎

在 Fcitx 线程上依次调用以下三步，必须在同一次调度里完成，不能拆开：

```cpp
libime::PinyinContext::setPendingKeyAlternatives(alternatives);  // [(字母, score), ...]
frontend->keyEvent(...);                                          // 发送这个字母键
libime::PinyinContext::setPendingKeyAlternatives({});             // 清空，防止串到别的键
```

可参照安卓 `Fcitx.sendKeyWithAlternatives` 和 `native-lib.cpp` 中的 `setPendingKeyAlternatives`。fcitx5-ios 的 `processKey` 已经在 `dispatcher->schedule` 里调用 `frontend->keyEvent`，在同一个 lambda 前后各加一行即可。

### 2.3 什么时候不传

以下情况不传落点数据，和谷歌拼音一致：

- 手指是从别的键滑过来的。
- 字符来自长按弹出的候选。
- 大写状态下的字母。传了引擎也会忽略，因为大小写对不上。

在设置里加一个开关「按落点智能纠错」，默认开。

## 3. 触摸手感：iOS 键盘界面各自实现

以下数值取自谷歌拼音 4.5.2，安卓已全部实现。iOS 视自身键盘框架取舍。

| 行为 | 谷歌拼音 | 说明 |
| --- | --- | --- |
| 手指滑出字母键 | 改为输入手指下的键 | 沿符号滑动方向的竖向滑动除外；离开按键 0.3 英寸才取消 |
| 双指交叠 | 第二指落下时立即输入第一指的键 | 字母、符号、空格、退格、逗号适用，Shift 和切换键除外 |
| 滑过来的键的长按 | 长按时间乘以 1.6 | 防止滑动途中误触发长按 |
| 第二行两端 | a、l 的触摸区延伸到屏幕边缘 | |
| 上下滑出符号 | 16dp，约 2.5mm | |
| 删除键连删 | 按下 400ms 后开始，之后每 50ms 删一个 | |
| 空格滑动移光标 | 每个字符约 2.8mm，按下 200ms 后才开始 | 快速点空格时不会误移光标 |

## 4. 验收

安卓的设备端测试可以作为 iOS 用例的蓝本：

- `PinyinTouchCorrectionTest`：
  - 输入 nihqo，只有落点靠近 a 时才出「你好」。
  - 输入 nihai，落点在 i、o 交界时「你好」排前三，落点在 i 中心时排不上来。
  - 上屏后立即退格撤销学习，中间按过别的键则保留学习结果。
- `KeyboardTouchTest`：滑出改键、竖向滑动出符号、双指顺序、两端触摸区、落点概率的取值。

## 5. 按谷歌拼音词库对齐候选顺序（2026-11-09）

谷歌拼音的用户词库按「打的编码 → 选的词 → 次数」记录，例如 `xg → 香港 ×907`、`bang m → 帮忙`。拼音插件新增一张同样的表 `pinyin/user.typed`（`typedcodehistory.h`），已合进 `patches/fcitx5-chinese-addons/0001-google-pinyin-learning.patch`：

- 导入谷歌词库时，所有条目都写进这张表，包括缩写、中英混合（`app里`）和英文。只有单个字母的英文不写，它们多半是在英文模式下打的。
- 每次上屏都给「打的编码 → 上屏的词」加一次。经过纠错的上屏不记在打错的编码下。
- 完整输入命中表里的编码时，表里的词排在最前，中英文一起排。排序分数是 `log10(次数)` 加两项最近选词加分：
  - 选过的词 `+3 × 2^(−距今上屏次数/5000)`；
  - 同一编码里最后选的那个词再 `+2 × 2^(−距今上屏次数/100)`。

  导入的词条记作没在 fcitx 里选过，不加分，所以刚导入时还是按谷歌的次数排。
- 某个键有落点邻键时，把它换成邻键，查表里的词，用 `log10(次数) − 落点代价` 和精确匹配的词一起排序。分数低于 1 的不出。
- 表情候选放到前 5 个词之后；英文拼写提示要输入满 4 个字母才出现。
- 学过的英文也按落点纠错。

iOS 已经移植：主 App 解析出 `.typed` 和 `.english`，与 `import-<UUID>.tsv` 同名放置，键盘合并词库时一并处理。

调参用 `scripts/google-pinyin-benchmark.py` 和设备端的 `CandidateDumpBenchmark`。用法见脚本开头的说明。

最近选词加分用 `scripts/typed-history-simulation.py` 调。它把谷歌词库当初始状态，按次数生成 50 万次上屏，统计两种情况下首选是否命中：编码的用法不变，以及随机 300 个编码改用第二个词（模拟换习惯）。用这份词库测的结果如下：

| | 用法不变 | 换习惯后第 1–10 次 | 第 11–50 次 |
| --- | --- | --- | --- |
| 只按次数 | 96.0% | 15% | 23% |
| 加最近选词加分 | 95.3%–96.4% | 77%–78% | 96%–98% |

「用法不变」的范围取决于是否模拟同一话题连着打：不连着打时略低，连着打时略高。
